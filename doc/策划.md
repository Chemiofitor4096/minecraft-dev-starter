# MC 开发工程助手 · DSH 插件策划

> 版本 v0.1 · 2026-10-30 · 状态：**待审核**
> 审阅入口：第 15 节「待确认决策」。机制依据见 `doc/调研-DSH插件机制.md`。

---

## 1. 现状与问题

### 1.1 已装插件覆盖了什么

本机 desktop profile（`~/.dsh/profiles/desktop`）已经装了 `minecraft-dev@0.10.1`，它以 cordis bundle 形式挂了 8 个技能、3 个工具（`mc_scaffold` / `mc_gradle` / `mc_codex`）和 4 个子代理。其中：

- `mc_gradle` 能跑 `runClient`，但它是一次**前台工具调用**：输出在单次调用内收集，600s 超时后杀进程树，调用结束才算回合结束。
- 项目信息没有任何地方沉淀：模型每次都要现场读 `build.gradle` 才知道这是 Fabric 还是 NeoForge。
- 没有"实例"概念：谁在跑、跑了多久、日志在哪、怎么停，全靠模型临时拼。

### 1.2 缺口

用 `mc_gradle` 跑一次客户端，等于把一个持续 10 分钟到几小时的图形程序塞进一次工具调用。这条路在演示里能过，日常开发过不去：

| 问题 | 具体表现 |
|---|---|
| 回合被占死 | 客户端跑着，模型什么都不能做，也没法问用户"窗口起来了吗" |
| 无法停止 | 只有一个超时开关，想提前关只能杀进程 |
| 无状态 | 重启 DSH 后不知道上次那个 java 进程还在不在 |
| 无归因 | 崩了以后要看 `logs/`、`crash-reports/`，位置因 loader 而异 |
| 无画像 | 17 个工程里哪个是 1.21.1 NeoForge、哪个用 JDK 21，没有一处可查 |

所以真正要做的不是"再包一层 gradlew"，而是：

1. **识别**——把工作区里的工程翻译成结构化画像（loader / MC 版本 / 加载器版本 / Java / Gradle / 元数据 / 可启动目标 / 风险）。
2. **托管**——把 `runClient` / `runServer` 当成"实例"启动：后台、可列、可读日志、可停、退出后自动归因。
3. **可扩展**——启动方式抽象成适配器，后续接 HMCL / PCL2 / Prism 这类现成启动器的实例库。

## 2. 目标与边界

### 2.1 目标

| 编号 | 目标 | 判定标准 |
|---|---|---|
| G1 | 识别工作区中的 MC 工程 | 对 `C:\Projects` 抽样 17 个工程，loader + MC 版本判定全对；无特征的工程明确报 `unknown` 而不是猜 |
| G2 | 托管启动 | `mc_launch` 在就绪超时（默认 90s，可配）内返回"已启动"而不阻塞回合；进程在 DSH 重启后仍可查询/停止；日志可增量读 |
| G3 | 可扩展启动方式 | 启动路径走适配器接口，新增一种启动方式不改工具层 |
| G4 | 模型可用 | 6 个工具的描述能让模型在"这个项目是什么 / 帮我起客户端 / 怎么崩的"三种问法下选对工具 |

### 2.2 非目标（MVP 明确不做）

- 下载、安装 Minecraft / Mod / 整合包；微软账号登录与正版校验。
- 替代 IDE、支持断点调试、热重载。
- 远程服务器托管、多人联机。
- macOS / Linux 的一等支持（代码保持跨平台写法，验收只看 Windows）。
- 修改用户的 `build.gradle`。插件只读工程，只写自己的状态文件与日志。

### 2.3 与 `minecraft-dev` 的关系

不复用它的代码，也不改它的包。理由：

- 它是别人维护的 npm 包（`minecraft-dev`），版本在外部演进，直接 import `lib/run-process.js` 等于把内部实现当 API。
- 职责不重叠：`mc_gradle` 是"前台构建/测试"，`mc_launch` 是"托管运行"。两者可以并存，工具描述里写清分工即可。
- 若后续要打通，走接口而不是 import：让 `mc_launch` 在检测到 `mc_gradle` 时提示"构建请用 mc_gradle"，仅此而已。

## 3. 使用场景

**S1 接手一个陌生工作区**
> 「这个项目是什么？能跑吗？」
→ `mc_project_show` 直接给出：NeoForge 1.21.1 / neo 21.1.251 / modDev 2.0.141 / JDK 21（`java.toolchain`）/ Gradle 9.5.0 / 可跑 `runClient`，并附证据（`build.gradle` 的 `net.neoforged.moddev`、`gradle.properties` 的 `neo_version=21.1.251`、`src/main/templates/META-INF/neoforge.mods.toml`）。

**S2 起客户端**
> 「帮我起客户端」
→ `mc_launch` 返回 `launchId=launch-3, pid=28104, log=...`，12s 后补一句"窗口已起（日志命中 `Backend library: LWJGL`）"。

**S3 崩了**
> 「刚才那次怎么崩的」
→ `mc_launch_logs` 尾部 + 自动归因："Gradle 构建失败：`Could not resolve net.neoforged:neoforge:21.1.251`，检查网络或离线缓存。"

**S4 客户端 + 服务端联调**
→ 同一工程两个实例并行，各自日志；端口冲突时从日志里识别 `Address already in use` 并给出建议。

**S5（后续）用现成启动器**
> 「用 HMCL 里那个 1.21.1 实例起一下」
→ 适配器列出实例库、挑版本、直启 java，不驱动 HMCL 的 GUI。

## 4. 形态：为什么是 DSH 插件

| 选项 | 结论 |
|---|---|
| DSH 插件（cordis bundle） | **采用**。能注册工具（`ctx.tools`）、持有长生命周期服务、读会话 cwd、走 profile 的 patch 层安装，与现有 `minecraft-dev` 同构 |
| MCP server | 否。要单开进程、自己实现协议，拿不到 host 的会话上下文与工作区信息，安装也重 |
| Skill | 否。skill 只能教模型"怎么做"，不能持有进程、不能持久化实例状态 |
| 外部 CLI 工具 | 只作为兜底。插件把检测/启动逻辑放在宿主进程里，才能做跨会话状态与日志跟踪 |

组成：

- **host 侧（必需）**：工具 + 两个服务（工程画像、启动实例）。纯 Node ESM，无原生依赖。
- **client 侧（可选，M5）**：右下角侧栏面板，列工程与实例、按按钮启动、看日志。机制参照已装的第三方插件 `dsh-better-sidebar`（`dsh.client.inject` + `platform: web`）。

## 5. 架构

```
                        DSH host 进程
  ┌───────────────────────────────────────────────────────────┐
  │  mcdev (cordis 插件包)                                     │
  │                                                           │
  │  tools.js ── mc_project_scan/show  mc_launch/list/...      │
  │     │                                                     │
  │     ├─▶ ProjectScanner   读文件 → 证据 → ProjectProfile    │
  │     │      └─ cache（按 mtime 失效）                       │
  │     └─▶ LaunchService    实例状态机 + 子进程 + 日志环形缓冲 │
  │            ├─ LaunchStore  $DSH_HOME/mc-dev-starter/*.json │
  │            └─ LauncherAdapter: gradle（本期）/ hmcl（后续）│
  └───────────────────────────┬───────────────────────────────┘
                              │ detached spawn
                    cmd.exe → gradlew.bat runClient
                              │
                   gradle daemon ──▶ java ──▶ 游戏窗口
```

### 5.1 插件行（同一个 npm 包，多入口）

| patch 行 id | 入口 | inject | 职责 |
|---|---|---|---|
| `mcdev-projects` | `minecraft-dev-starter/projects` | `tools` | 扫描与画像工具 |
| `mcdev-launch` | `minecraft-dev-starter/launch` | `tools` | 启动/停止/日志工具，持有 `LaunchService` |
| `mcdev-ui`（M5） | `minecraft-dev-starter/client` | client 包 | 侧栏面板 |

拆成两行而不是一行：识别可以单独关掉（比如只想用启动功能），也方便日后把识别能力复用到别的插件里。

### 5.2 依赖面

只依赖 `@deepseek-ai/dsh-tools`（`defineTool`）、`@deepseek-ai/schemastery`（Config）、`@deepseek-ai/cordis`（peer）。不依赖 `dsh-subprocess`、`dsh-jobs`——原因见 7.2。

## 6. 功能 A：工程识别

### 6.1 扫描策略

- **根**：会话 cwd（`exec.agent.session.header.cwd`），允许参数覆盖。一次扫描不跨出工作区。
- **深度**：默认 3，BFS。
- **剪枝**：`.git` `.gradle` `build` `out` `bin` `run` `.idea` `node_modules` `libs` `reference` `.dsh`。
  这一条不是洁癖：`tmachines` 的 `reference/` 下有三个依赖的 `mods.toml`，不剪就会把 Create 认成本工程的元数据。
- **候选**：目录内存在 Gradle 构建文件（`build.gradle(.kts)` / `settings.gradle(.kts)`）、loader 元数据文件或 `gradlew`。
- **多模块**：读 `settings.gradle(.kts)` 的 `include`，把模块目录补进候选；Architectury 的 `fabric/` `forge/` `common/` 由 `include` 自然带出。
- **预算**：最多扫 2000 个目录、返回 120 个候选；触顶时返回 `truncated: true`，不静默截断。

### 6.2 证据分层与判定表

识别结论必须带证据，模型和用户才能判断该不该信。证据分三级：

- **强**（定 loader）：构建脚本的插件声明、元数据文件。
- **中**（定版本）：`gradle.properties`、构建脚本里的版本字面量、元数据的 `depends`。
- **弱**（定可用性）：wrapper 版本、`run/` 目录、`build/libs/*.jar`、IDE 配置。

| 识别为 | 强特征 | 元数据（优先级从高到低） | 版本来源 |
|---|---|---|---|
| Fabric | `fabric-loom` / `net.fabricmc.fabric-loom` | `src/main/resources/fabric.mod.json`、`src/main/templates/fabric.mod.json` | `gradle.properties` 的 `minecraft_version`；次选 `depends.minecraft` |
| NeoForge | `net.neoforged.moddev`、`net.neoforged.gradle.userdev` | `META-INF/neoforge.mods.toml`、`META-INF/mods.toml` | `minecraft_version`；`neo_version` 前缀映射（21.1→1.21.1） |
| Forge | `net.minecraftforge.gradle`（FG1.2 / FG3 / FG5 / FG6）、`net.minecraftforge:forgegradle` | `META-INF/mods.toml`、`mcmod.info` | 构建脚本 `minecraft { version = "..." }`、`gradle.properties` |
| Paper | `paperweight`、`io.papermc.paper` | `paper-plugin.yml`、`plugin.yml` | `api-version`、`paper_api_version` |
| Spigot | `spigot-api` | `plugin.yml` | `api-version`、`spigot_version` |
| Architectury | `architectury` 插件、`dev.architectury.loom` | 子项目各自元数据 | 子项目汇总 |
| 未知 Gradle | 有构建文件，以上都不命中 | — | 只报 Gradle 版本，`loader: unknown` |

**占位符解析**：元数据里普遍写 `${mod_id}`、`${mod_version}`，直接读会得到字面量。规则是拿 `gradle.properties` 建一个 `key → value` 表做替换（也吃 `build.gradle` 里的 `ext` 与 `def` 常量）；替换不掉的字段保留原文并打 `unresolved` 标记，不猜。

**NeoForge 版本映射**：`21.1.251 → 1.21.1`、`20.4.237 → 1.20.4`、`20.2.x → 1.20.2`。映射表内置，命中不了就只报 neo 版本，MC 版本留空并给 warning。

**置信度**：`0.95`（强特征 + 元数据一致）/ `0.8`（强特征无元数据）/ `0.5`（只有弱特征）/ `0.2`（猜测，不给结论）。两条强特征互相矛盾时降低置信度并写 `conflicts[]`。

### 6.4 本机抽样校准（已做）

对 `C:\Projects` 下 17 个 Gradle 工程做过一次字段扫描（13 个 NeoForge、1 个 Fabric、1 个 Architectury、2 个无特征），发现的坑直接进了规则：

| 现象 | 处理 |
|---|---|
| `rationality` 等工程的元数据在 `src/main/templates/` 下，`resources/` 里没有 | 元数据查找路径同时覆盖 `templates` |
| Fabric 工程 `fabric.mod.json` 全是 `${mod_id}` 占位符 | 必须回落到 `gradle.properties` 解析 |
| `tmachines/reference/` 有 3 个依赖的 `mods.toml` | `reference/` 进剪枝表 |
| `Custom-Machinery-1.20.1` 顶层无 loom 字样，只有 `fabric/fabric.mod.json` | 靠 `include` 展开子项目判定 |
| `Kard` 用 `build.gradle.kts` | 规则同时匹配 Groovy 与 Kotlin DSL 写法 |
| `AnnoCore` 有完整 Gradle 但无 loader 特征 | 报 `unknown-gradle`，不硬猜 |
| `engineersmaterials`、`protectionengineering-1.21.1` 有 `bin/` 旧 Eclipse 产物 | `bin/` 进剪枝表 |

### 6.5 环境诊断

画像里带"能不能跑"的结论，而不只是"是什么"：

- **Java 需求**：MC 1.7.10/1.12.2 → 8；1.16.5/1.20.x → 17；1.21.x → 21；26.x → 25。取 `build.gradle` 的 toolchain / `sourceCompatibility` 覆盖默认值。
- **JDK 探测顺序**：项目配置 > `gradle.properties` 的 `org.gradle.java.home` > `JAVA_HOME` > `PATH` 的 `java -version` > 常见安装目录（`Program Files\Java`、`Program Files\Microsoft\jdk-*`、`Program Files\Eclipse Adoptium`）。
- **风险项**：JDK 版本与 MC 不匹配、wrapper 的 Gradle 太老跑不动当前 JDK、缺 wrapper、`run/` 首次运行要下载资源。

## 7. 功能 B：启动与托管

### 7.1 启动途径

| 途径 | 适用 | 本期 |
|---|---|---|
| wrapper `runClient` / `runServer` | mod / plugin 开发 | ✅ |
| 任意自定义 Gradle task | `runData`、`runServer` 变体 | ✅（`target: custom` + `task`） |
| 直启 java（读 `versions/<id>/<id>.json`） | 任意实例库 | 后续（M6） |
| HMCL / PCL2 / Prism 实例 | 通用启动器 | 后续（M6） |
| 复用 IDE 运行配置 | 需要调试器 | 可选（未排期） |

### 7.2 进程模型（本方案最关键的决策）

**不用 `ctx.subprocess`**：它的服务 dispose 会终止所有托管进程，而启动器要求游戏跨 DSH 会话存活。

**不用 `ctx.jobs`**：job 的语义是"agent 的后台任务"，owner 释放即取消，状态是 `running → completed`；游戏不是任务，是实例。

**采用** `node:child_process.spawn({ detached: true, windowsHide: true })` + `unref()`，自建 supervisor：

- 实例状态机：`starting → running → exited (normal | crashed | killed | failed)`
- 宿主进程退出不影响游戏；宿主重启后按 `pid + 启动时间` 对账，`process.kill(pid, 0)` 探活，探不到就把记录标为 `unknown`（不伪造 `exited`）。
- `mc_launch` 默认 `wait: "untilRunning"`：等日志命中就绪标记（客户端 `Backend library` / `LWJGL`，服务端 `Done (...)! For help, type`）或 90s 超时，然后带着 PID 返回——既不让回合被占死，也不让模型拿到一个"可能已经崩了"的假成功。
- 关窗退出与崩溃的区分：客户端窗口正常关闭 → exit code 0 且日志无 `crash-reports` 新文件 → `normal`；非 0 → `crashed`，并抓最新 `crash-reports/*.txt` 的头部。

### 7.3 Windows 细节

| 项 | 处理 |
|---|---|
| 调用 | `cmd.exe /d /s /c ""C:\proj\gradlew.bat" runClient"`，spawn 时 `windowsVerbatimArguments: true`（node 默认转义会让 cmd 解析失败；`mc_gradle` 已在真机验证过这套引号策略） |
| 停止 | `taskkill /PID <pid> /T /F` 杀整棵树；`/T` 不能少，否则 java 与 gradle worker 会活下来 |
| Gradle daemon | 不主动 `--stop`（daemon 复用能加快下次构建），文档里说明它是残留进程 |
| 中文输出 | Gradle 在中文 Windows 上可能输出 GBK；按替换字符比例判断，回退 `TextDecoder('gbk')` |
| 路径 | 全绝对路径 + 引号；含空格与中文的目录（`C:\Projects\基于...`）进回归集 |

### 7.4 日志与崩溃归因

- 落盘：`$DSH_HOME/mc-dev-starter/logs/<launchId>.log`，stdout/stderr 合并原样写入，不插时间戳（保持与 Gradle 原始输出一致，方便用户自己 grep）。
- 内存：每个实例保留最近 2000 行环形缓冲，供 `mc_launch_logs` 增量读。
- 归因规则（首轮）：

| 特征 | 结论 |
|---|---|
| `BUILD FAILED` + `Could not resolve` | 依赖解析失败，查网络/离线缓存 |
| `Unsupported class file major version` | JDK 版本不匹配 |
| `No matching toolchains found` | 缺对应 JDK |
| `OutOfMemoryError` / `Metaspace` | 调 `org.gradle.jvmargs` |
| `Address already in use` / `FAILED TO BIND TO PORT` | 端口占用（联调场景常见） |
| `Mixin apply failed` | 模组注入失败，指向具体 mixin 类 |
| 退出码 0 但日志有 `crash-reports` 新文件 | 记为 `crashed` 并附报告摘要 |

### 7.5 并发与资源

- 同一工程同一 `target` 同时只允许一个实例；客户端与服务端可并行。
- 同工程并发的 `gradle` 调用会争 daemon 与目录锁 → 启动前检查 `.gradle` 锁文件，必要时提示而不是硬上。
- 多个客户端同时跑（每个吃 2-4G）时在返回里给内存提示。

## 8. 工具清单

命名统一 `mc_*`，与既有 `mc_scaffold` / `mc_gradle` 同前缀。工具描述里必须写清与 `mc_gradle` 的分工，否则模型会混。

| 工具 | 用途 | 关键参数 | 返回 |
|---|---|---|---|
| `mc_project_scan` | 列出工作区里的 MC 工程（紧凑） | `root?`、`depth?` | `projects[]`（root/loader/mcVersion/kind/confidence）、`truncated` |
| `mc_project_show` | 单个工程完整画像 | `root` | 6.3 的完整结构 + `java.status` + `warnings` |
| `mc_launch` | 启动实例 | `root`、`target: client\|server\|custom`、`task?`、`javaHome?`、`extraArgs?`、`wait?: untilRunning\|detach\|untilExit`、`timeoutMs?` | `launchId`、`pid`、`status`、`logPath`、`readyMarker?` |
| `mc_launch_list` | 列实例 | `includeExited?` | `launches[]`（id/root/target/status/pid/startedAt/exitCode） |
| `mc_launch_logs` | 读日志 | `launchId`、`offset?`、`limit?`、`grep?` | `lines[]`、`nextOffset`、`truncated` |
| `mc_launch_stop` | 停实例 | `launchId`、`graceMs?` | `status`、`exitCode`、`killedTree` |

错误一律走结构化结果（`code` + `message` + `hint`），不抛异常结束回合：`NO_PROJECT`、`NOT_RUNNABLE`、`ALREADY_RUNNING`、`SPAWN_FAILED`、`TIMEOUT`、`UNKNOWN_LAUNCH`。

## 9. 配置与状态

**部署配置**（patch 行 `config`，schemastery）：

```yaml
- id: mcdev-launch
  name: minecraft-dev-starter/launch
  config:
    defaultClientTask: runClient
    defaultServerTask: runServer
    readyTimeoutMs: 90000
    defaultGraceMs: 8000
    logRingLines: 2000
    javaHomes: []          # 额外 JDK 搜索目录
```

**项目级覆盖**（可选，写进用户工程）：`<root>/.dsh/mc-dev-starter.json`，字段 `javaHome`、`tasks`、`extraArgs`、`displayName`。插件永远不主动创建这个文件，只在用户明确要求时写。

**状态**：`$DSH_HOME/mc-dev-starter/state.json`，只存实例记录（上限 100 条，滚动淘汰）与最近一次扫描的缓存指纹。不含工程源码信息以外的隐私数据。

## 10. 后续：通用启动器

### 10.1 适配器接口

```ts
interface LauncherAdapter {
  id: 'gradle' | 'java' | 'hmcl' | 'pcl2' | 'prism'
  probe(ctx): Promise<{ available: boolean, reason?: string }>
  listTargets(ctx): Promise<LaunchTarget[]>        // 版本/实例
  buildSpawnPlan(target, opts): SpawnPlan          // argv/cwd/env
  classifyLog?(lines: string[]): Marker[]          // 就绪/崩溃标记
}
```

工具层只认 `LaunchTarget`，不认具体启动器；新增适配器不动工具。

### 10.2 各目标的现实情况

- **HMCL**：没有一个稳定的、可承诺的 CLI（这点需要在 M6 开工前实测 `hmcl.exe --help` 与源码，不先写进需求）。它真正的价值是实例库与版本 JSON。所以推荐路线是**读实例目录 + 自己拼 java 命令**，而不是驱动 HMCL 进程。
- **直启 java**（M6 的主体）：读 `versions/<id>/<id>.json` 的 `libraries` / `arguments.jvm|game` / `mainClass` / `assetIndex`，解压 natives，拼 classpath。这条路同时覆盖官方启动器、Prism、PCL2、HMCL 的实例目录，工作量估 5-8 人日，是本项目里最重的一块。
- **PCL2 / Prism**：同上，靠实例目录兼容，不需要单独适配器，先按目录格式识别。

### 10.3 分阶段

M6 先做"能列出实例 + 直启 vanilla/已装好的 Fabric 实例"，再补 Forge/NeoForge 的 launchwrapper/模块化启动差异。

## 13. 测试策略

1. **规则单测**：`test/fixtures/` 里放最小工程树（fabric / neoforge / forge-1.12 / paper / architectury / unknown），断言 loader、版本、置信度、evidence。
2. **真实回归**：对本机 17 个工程跑扫描，输出快照对比（不联网，不构建）。
3. **argv 单测**：Windows 引号、空格、中文路径、`--args` 透传。
4. **进程集成**：用一个假的 `gradlew.bat`（打印就绪标记后 sleep）验证 detached、就绪判定、tree kill、状态对账，不依赖真的游戏。
5. **编码单测**：GBK 与 UTF-8 混合输出各一份样本。
6. **手动冒烟**（每次发版）：起一个 Fabric 客户端 + 一个 NeoForge 客户端，确认窗口出现、`mc_launch_stop` 能关掉、无孤儿 java。

## 14. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 插件 API 与桌面版 DSH 版本漂移 | 加载失败或工具不出现 | peer 范围对齐已装插件（`^0.1.5-rc.1 \|\| ^0.1.7-rc.1 \|\| ^0.2.0-rc.2`）；M0 先验证；把 cordis/schemastery 调用收敛到一处适配层 |
| 进程树杀不干净（java 逃逸） | 残留进程吃内存，用户观感差 | `taskkill /T /F` + 启动后记录子进程；冒烟里专门查孤儿 java |
| 首跑 Gradle 下载依赖很慢 | 就绪超时被误判为失败 | 区分"构建中"与"已失败"：命中下载/配置日志时延长等待并给出提示 |
| 识别误判 | 用户信任崩塌 | 一切结论附 evidence；矛盾时降置信度并明说；`unknown` 是合法答案 |
| 长任务把宿主拖死 | DSH 卡顿 | 扫描走异步 IO + 深度/数量预算；日志只留环形缓冲 |
| 安全：启动任意命令 | 越权执行 | `target` 只映射预定义 task；`custom` 需显式 `task` 且限制在工程目录内；不执行用户输入的 shell 字符串 |
| HMCL 无稳定 CLI | M6 方案落空 | 已把 M6 主体改成"直启 java + 实例目录兼容"，不赌 HMCL 的命令行 |

## 附录 A：已核实事实与出处

详见 `doc/调研-DSH插件机制.md`。要点：

- 插件 = npm 包 + `dsh.bundle.patch` 指向的 `cordis.patch.yml`，`dsh plugin add` 会把它并进 profile 的 bundle 栈。
- 插件入口导出 `name` / `inject` / `Config` / `apply(ctx, config)`；工具用 `defineTool` 注册到 `ctx.tools`。
- 桌面版 DSH 加载的是 `~/.dsh/profiles/desktop`（host 进程命令行可证）。
- 用户 patch 层（`cordis.patch.yml`）支持 `file://` 绝对路径挂载，是当前最轻的本地开发方式。
