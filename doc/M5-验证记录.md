## 1. 四个工具

| 工具 | 作用 | 关键参数 |
|---|---|---|
| `mc_projects` | 列工作区里的工程与可运行目标 | `root?`、`refresh?` |
| `mc_launch` | 启动一个目标，默认等运行态再返回 | `taskPath`、`root?`、`wait?: ready\|detach`、`timeoutMs?` |
| `mc_launch_logs` | 读日志，异常退出附归因 | `id?`、`root?`、`offset?`、`limit?` |
| `mc_launch_stop` | 停止实例（含进程树） | `id?`、`root?` |

都是 `/mcdev/api` 方法表的薄封装：工具不复制业务逻辑，面板与模型看到的状态天然一致。省略 `id` 时用"当前工程活跃实例"，省掉模型先查再停的两步。

## 2. 依赖问题与解法

`link:` 安装的插件，Node 从仓库真实路径解析，**看不到 profile 里的 `@deepseek-ai/*`**。所以工具不能靠"运行时提供"。

解法是把它作为普通依赖装上，并且**版本对齐桌面运行时**：

- 从 `DSH NEXT/resources/app.asar` 里读出桌面版实际版本：`dsh-tools@0.2.1-rc.3`（同时确认 `dsh-package-manifest`、`dsh-client-ui-slots` 同为 0.2.1-rc.3）。
- `package.json` 里写进 `dependencies`（发布后 `dsh plugin add` 会一起装），本地 `pnpm add` 同一个版本。
- 好处：`defineTool` 的参数 DSL、输出 schema 校验与实际运行时一致；坏处：多一份副本（约几十 KB，纯 schema 逻辑，无服务注册）。

顺带验证了**跨版本不炸**：m0test profile 是 0.1.5 运行时，用 0.2.1-rc.3 的 `defineTool` 注册四个工具后插件照常激活（`host ready` 正常打印）。说明这套 DSL 在两代之间兼容。

m0test profile 启动后宿主日志正常：

```

```

没有出现 "plugin tree failed to load"，说明 `inject: ['tools']` 与四个工具的注册都被接受。

## 5. 已知限制

1. **模型侧 schema 没法在本轮肉眼确认**：需要挂到真实会话里看工具列表。桌面版挂载会重启 DSH、中断当前会话，所以留到下一次。
2. **工具与面板的日志标签不联动**：AI 起实例不会替人切标签（有意为之，工具调用不该抢界面）。
3. **`mc_launch` 等待上限 60s**：首次构建常常超过，超时返回 `timedOut: true` 并给出日志入口，不当作失败。
